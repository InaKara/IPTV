## Conclusion and remaining work

The sampled server does accept nonzero ranges and this MP4 supplies duration/keyframe/index structures. Therefore a simple claim that the movie is wholly unseekable or the server refuses every range is unsupported. The relatively large front index may increase preparation work; that is a hypothesis rather than the diagnosed cause of the user's seek/resume failure. Slow seek loading/decoding, invalid offsets/timestamps, selected-track behavior and app capability/progress handling remain candidates.

A user-confirmed working movie title was requested but has not yet been supplied. The alternate same-title route is an unsuccessful reference sample, not proof of a working comparison. No actual Android timeline, seek command, player error, saved position or post-seek decoding was observed. PC evidence cannot establish whether the app incorrectly rejects/handles a seek, the selected stream fails on the device, or both. The pending first-READY resume capability timing noted in the MD-4 review is still only a source hypothesis.

Do not enable approximate seeking, enlarge buffers, alter decoder dependencies, switch sources automatically, clear saved progress or promise a fix from these headers. Next useful evidence is a specifically approved Firestick reproduction with the failing source and a user-confirmed working control, observing actual duration/seekability/seek result/error and saved/resumed position. Prepare that bounded diagnostic session for review before device access or new diagnostics/playback changes; current MD-4 approval does not include it.

The official [Media3 troubleshooting guidance](https://developer.android.com/media/media3/exoplayer/troubleshooting) explains index-dependent seeking and the separate loading/keyframe work involved in a video seek. It does not diagnose this provider movie. VOD-009 remains Partial: bounded PC discovery completed, source/device cause and any playback correction unresolved.

The failure now has direct device evidence of memory exhaustion during movie loading/playback and a confirmed OOM crash during Resume. Source/network capability alone is not the explanation. Which allocations dominate is not isolated: the default sample-buffer target, the 22.8 MB MP4 index, parser/track state and browser/application state all need headroom. The installed player's unmodified automatic video/audio target is 137.5 MiB, with 50-second min/max defaults; it is a target rather than a measured allocation total.

[MP-1 / REL-006](../design/VOD_MEMORY_REVIEW.md) proposes a smaller explicit VOD sample-buffer target as the focused next change. No buffer/player/dependency change was implemented during this session.
