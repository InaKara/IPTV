## Choices and tradeoffs

- **Startup:** reuse the existing Compose branding and connection state, keeping snapshot/network ownership in the current ViewModel. This is a small presentation/routing change. A startup-ready handoff must include initial browser preparation so a loading panel does not flash after the logo. Do not fabricate percentages or add another delay once the browser is ready. A full navigation or splash architecture replacement is unnecessary for this scope.
- **Logos:** fit into available space rather than zoom/crop. This enlarges artwork while preserving provider image proportions and the label/grid. Removing padding embedded inside the downloaded image would require different image processing and could cut off legitimate artwork.
- **Audio:** an unsupported codec, wrong/missing audio track, malformed source or output-route problem can all produce silence; the channel name does not distinguish them. Prefer an evidence-based existing-API correction. A software audio decoder could expand compatibility but adds native binaries, build/maintenance work and codec-license considerations; it is not selected or authorized here. No general Media3 upgrade is proposed. Standard ExoPlayer uses Android platform decoders unless extensions are included; see [Android's supported-format documentation](https://developer.android.com/media/media3/exoplayer/supported-formats).
- **Controls:** retain PlayerView and fix focus styling/key ownership instead of building a full Compose controller. The proposed Menu interaction preserves familiar hidden-controller shortcuts while making visible controls navigable. The visible-controller arrows/OK and first Back behavior are explicit proposed changes requiring review. Historical channel-direction and VOD Stop decisions remain separate.

## Answers from the current implementation

### Can categories be classified as live TV or VOD?

Yes, with different confidence levels. Today M3UParser assigns each **entry** an isVod Boolean using category words (`vod`, `movie`, `series`, `film`, `on demand`), URL paths (`/movie/`, `/series/`, `/vod/`) or file extensions (`.mp4`, `.mkv`, `.avi`, `.mov`). Everything else falls back to live. There is no explicit Unknown state and no category-level type/filter in the browser. These are guesses: a live movie channel can match a category keyword, and VOD can lack a recognizable path/extension. File extensions alone are not authoritative proof.

A category can be summarized from its entries, allowing mixed/uncertain results rather than forcing every group into two types. A provider's structured Xtream-compatible API can instead expose separate live/movie/series category/stream collections. An [API implementation](https://github.com/gtaman92/XtreamCodesExtendAPI/blob/master/player_api.php) demonstrates live/movie categories and streams. Availability/accuracy on this particular server is unverified. Recommendation for a later proposal: prefer explicit provider type where supported, with cautious M3U fallback and mixed/unknown handling. No filters, ordering changes or API calls are introduced by this review.

### What server information is currently unused?

The app requests only `get.php` with `type=m3u_plus`. It retains entry display names, stream addresses, group-title, tvg-logo, tvg-id, tvg-name, user-agent and optional tvg-chno. Names/groups/logos/stream/user-agent/provider number are used by browsing/playback. tvg-id and tvg-name are retained in channel snapshots but have no programme-guide consumer or other current UI use. A tvg-id is an identifier, not programme data.

An **existing private playlist saved on 22 October 2026** was inspected offline, without printing its values or making a new request. It has 100,915 entries, all with group-title, tvg-id, tvg-name, tvg-logo and user-agent attributes; 266 tvg-id values are nonblank. No tvg-chno, extra playlist directives or header EPG address are present in that saved response. The current server response may differ. No current server capability is inferred from this older artifact.

M3U playlists can advertise a separate XMLTV EPG address in their header; the app currently ignores such header metadata. [IPTV-org's playlist documentation](https://github.com/iptv-org/iptv/blob/master/docs/playlists.md) gives an `x-tvg-url` example. Compatible provider APIs may offer current/next programme data, detailed VOD metadata and account/server information; the [example API implementation](https://github.com/gtaman92/XtreamCodesExtendAPI/blob/master/player_api.php) contains short EPG, VOD info and user/server response handling. XMLTV/EPG is not automatically included simply because the M3U contains EPG IDs. These capabilities have not been checked against this account/server. The current app does not request or display programme listings. The earlier BR-1 programme-data exclusion remains in force until a new feature is explicitly proposed and approved.

### How do Favorites work now?

1. Focus a channel tile in a category, Search or Favorites.
2. Press the remote **Menu** button (three horizontal lines).
3. Choose **Add Favorite** and press OK. A saved favorite instead offers **Remove Favorite**.
4. Open the **heart** in the left sidebar to view Favorites.

Keyboard Context Menu/Shift+F10 uses the same action. Category tiles do not offer it. Favorites are stored per account across restarts and resolved against the current playlist, in playlist order. The action closes and returns focus without starting playback. This is source-confirmed behavior under BROWSE-011; physical remote acceptance remains separate.

## Audio findings and approved AU-1 implementation

The approved bounded PC metadata request on 23 October found H.264 video and **MP2 stereo audio at 48 kHz** on the reported TRT 1 HD entry. The user then explicitly approved read-only codec inspection after asking why a common codec would be missing. Six system/vendor codec configuration files were read over the debugging transport. They advertise `OMX.google.mp3.decoder` for `audio/mpeg`, with no `audio/mpeg-L2`/MP2 declaration. MP3 and MP2 are different formats; a registered MP3 decoder does not itself advertise MP2 support to Media3. This strengthens the missing-decoder explanation, but XML declarations do not substitute for runtime MediaCodecList/selected-track/output evidence. No app was started, stopped, installed or navigated, and no setting changed.

No audio was played through the Firestick. The response has an audio track; this does not establish that its samples are non-silent. The PC probe and approved read-only inspection are separate from the synthetic/local smoke suite; authenticated addresses, raw probe output and device configuration stay under ignored build reports.

PLAY-008 adds fixed-vocabulary debug diagnostics for available/supported/selected tracks and codec/output failures, with no provider labels, addresses, credentials, decoder names or raw exception causes. No speculative device setting or generic renderer fallback can supply a codec that is absent.

**AU-1 / PLAY-010 approved on 23 October 2026:** the user explicitly requested implement mp2 software-decoder route, selecting this previously documented proposal. Integrate the official Media3 FFmpeg audio extension at the existing 1.2.1 version, narrowly configured for MPEG audio, using platform decoders first and the software renderer only for unsupported formats. Keep current codecs/player versions and data unchanged. Local native build/packaging/decoding checks are included; deployment and device playback remain separately approved actions.

Tradeoffs: native libraries increase APK size and add ABI, source/license and build maintenance. The [official 1.2.1 extension instructions](https://raw.githubusercontent.com/androidx/media/1.2.1/libraries/decoder_ffmpeg/README.md) require a manual FFmpeg/NDK build, recommend FFmpeg 6.0, support Linux/macOS and do not directly support Windows. Reproducible source build, tool availability and ABI packaging must be established; do not substitute an arbitrary third-party prebuilt AAR. The completed local build measurements are recorded below; development tool downloads remain on the PC, not in the APK. This proposal does not authorize a global toolchain upgrade, deployment, playback test on the Firestick or additional server features.

Acceptance: a local synthetic MP2 fixture must decode to valid non-silent PCM, the APK must contain/load the required native ABIs, fallback selection must retain platform preference, and supported existing audio must remain usable. Physical audible playback is separately authorized and recorded. PLAY-008 and PLAY-010 remain Partial until the remaining Android/audible acceptance is established; local decoding/build evidence does not by itself establish TRT 1 sound.

Earlier decision: asking about complexity alone did not approve AU-1. The later explicit implementation request on 23 October now approves this decoder/native-build scope.
