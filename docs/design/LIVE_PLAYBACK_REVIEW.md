# Live playback controls — LP-1 local implementation

23 October 2026. **PLAY-012 explicitly approved with Approve LP-1 implementation on 23 October 2026.** Local implementation/checks authorized; physical acceptance remains separate. The user requested live rewind/forward and a Live action, then asked for a recommended button implementation. AU-1/PLAY-010 is separately approved and can proceed independently. No deployment/app start is included.

Approved behavior:

- Keep on-screen and dedicated Rewind/Forward as **10-second steps**, clamped to the oldest/newest available seekable position. They do not jump across the entire window. Preserve existing VOD hidden Left/Right 30-second shortcuts and dedicated 10-second increments.
- Add **Live** on the lower playback bar for live media. It jumps to the player's default live position, allowing the stream's normal safety delay instead of seeking beyond playable data. Forward remains a step; Live is the direct catch-up action. Make Live remote focusable with existing amber styling, and indicate when playback is at the live edge.
- Use an available equivalent HLS live feed for the currently supported provider where it can be validated, while retaining the original channel identity/favorites/history references. Keep original playback as a fallback when that alternative fails. Do not reinterpret VOD URLs or arbitrary external streams. No service-wide API migration is included.
- Enable seeking only for an actual seekable timeline. Nonseekable/unknown-window feeds retain disabled seek controls; no recording/DVR storage is invented. Available history can be only about a minute, and changes as the provider window moves.
- For live playback, show lag behind live (for example -00:25) and a Live state instead of presenting window duration as programme length. Keep VOD elapsed/total time. The current two numbers are Media3's current position and duration: for live, duration may be a rolling window or unknown.
- If a long pause falls behind the available window, recover to the default live position with clear feedback rather than leaving an unexplained error. Ordinary unrelated stream failures retain existing error handling.
- Preserve controller focus, Menu reveal, three-second timeout, Back behavior, dedicated media actions and player release. A newly added Live action must not steal focus while another control is being used.

Tradeoff: step buttons preserve precise navigation and existing increments; the separate Live action provides a quick return. HLS source selection and dynamic-window recovery need actual capability checks, not just removing the current VOD guard. Keeping playback-source selection separate from canonical identity avoids invalidating saved favorites/history.

Local validation uses synthetic local HLS/progressive capability fixtures and native control tests for seek enablement/bounds, changing/expired windows, source fallback, identity retention, Live action/focus/status and preserved VOD/key behavior. Run fresh smoke/lint and a debug build. Physical provider playback/audio/remote acceptance remains separate.

Implementation details within the approved scope: identify candidate routes only by exact configured origin/base path and account credentials with numeric live IDs; accept both provider root TS and /live/ TS forms. Media3 parses/validates the alternative HLS manifest and timeline; no extra preflight request. Ignore placeholder timelines when validating live type. HLS failure/non-live manifests fall back once to the exact original URL. Keep hidden Left/Right VOD-only; live uses on-screen/dedicated 10-second buttons. Live lag is distance behind the default safe live position, so Live is not presented as programme duration or encoder latency. Recovery is bounded against repeat-error loops and retains pause/play intent.

## Implementation and local evidence — 23 October 2026

Provider/account-bound source selection accepts exact root-style and /live/ numeric TS routes, with URI-encoded credentials and origin/base-path matching. It leaves VOD, existing HLS, external origins, query/fragment variants and mismatched accounts untouched. Media3 HLS parsing/timeline preparation validates the candidate without a duplicate preflight request. Placeholder timelines are ignored; a known non-live timeline or alternative-source error falls back once to the original URL, retaining the canonical channel object. Alternative-source requests use zero extra retries before fallback; the original route retains the normal policy.

The common player wrapper and dedicated-key helper enforce actual seekability, known duration and current bounds. Both native step labels now show 10. Live seeks use only live timelines; hidden D-pad VOD 30-second shortcuts remain unchanged. Live uses seekToDefaultPosition, not the absolute window end. Lag measures distance behind that safe default; unknown values show an em dash. The lower time area hosts a focusable amber Live action and hides the original live elapsed/total labels. Position polling runs only for attached, visible live controls and does not reset the three-second timeout. Listeners and polling are removed on detach/release. Updates leave another focused control alone; unavailable focused Live returns to an enabled control even when Play/Pause is temporarily unavailable.

Behind-live-window errors recover with brief feedback, preserving play/pause. Immediate retries are bounded per pause and by a 30-second cooldown; persistent alternative failure falls back once, and other original-source errors retain the normal error screen. This does not add a DVR cache or programme data.

Six new stable cases (TC-APP-101–106) cover origin/account/route boundaries and canonical retention; shared live/VOD commands and changing bounds; recovery/cooldown/intent/fallback; a real Media3 HlsMediaSource loading synthetic rolling manifests and rejecting invalid data; native Live/lag/amber pixels/remote reachability/enablement/focus cleanup; and live-to-VOD time/key/timeout transitions. The dynamic fixture rereads data on each open because the playlist tracker reuses its DataSource. Native snapshots require a completed drawing frame; earlier incomplete snapshots were fixture timing artifacts, not hidden production buttons. Rendered live and VOD controls were inspected.
