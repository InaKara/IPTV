## Read-only findings

### Movies already use one full download

LibraryRepository.refresh requests get_vod_categories and get_vod_streams without a category parameter, streams the whole listing to SQLite and marks it fresh for 24 hours after a successful transaction. Category selection queries local pages; a fresh catalog ordinarily causes no provider download. LibraryViewModel nevertheless sets loading immediately on each nested navigation and republishes a pending state even when refresh will return without a request. Every displayed page also prepares selected aliases against the legacy playlist. This explains a misleading repeated loading path; actual device category latency and request counts are not measured here. A canceled/failed initial download or expired catalog can genuinely require another attempt.

Proposed LIB-005: complete the single full movie-catalog load when Movies is entered, reuse it for category switches and page/sort/filter actions, and show Loading/Updating only for real pending work. Keep the 24-hour freshness rule, failure-only explicit retry, cached usable data and account-safe cancellation. Avoid repeated full reconciliation for already prepared pages. Keep database paging and visible artwork instead of retaining all movies/posters/details in RAM. Selected movie details still load on demand; startup/VOD's five-tile root still does no catalog work. A cache load is distinct from a provider re-download; neither should create a misleading full-catalog spinner on each category switch.

### Reproducible episode-identity loss

LibraryParser.fields flattens nested info fields into the same map as top-level fields. An info.id encountered after an episode's top-level id can overwrite it. LibraryDatabase entries are keyed by cache/kind/id and inserted with CONFLICT_REPLACE; repeated overwritten IDs therefore collapse rows, potentially across seasons. The seasons list is derived from surviving episode rows.

A read-only one-off invocation of the already compiled parser, using a synthetic InputStream (not a new implementation testcase), supplied episode IDs 101, 102 and 201 across seasons 1 and 2. Each nested info contained the same metadata ID 900. Actual parser output was [900, 900, 900], one unique identity. This confirms an app defect for that response shape, not that the affected real series has been inspected. The existing synthetic episode fixture contains duration-only nested info and did not cover this collision. No provider or Firestick was accessed.

Proposed LIB-006: keep top-level playable episode IDs, title/container/episode fields and actual enclosing series/season identity separate from optional nested descriptive metadata, independent of JSON field order. Preserve every distinct valid episode supplied for the selected series; missing/invalid route IDs must not be silently replaced by a descriptive metadata ID. Retain existing account/type/duplicate safeguards, bounded selected-series cache and paging, watched filter and adult category rule. Invalidate/refetch old affected selected-series caches after the correction without clearing durable favorites/progress or fetching all series. Rebuild only that series atomically; failures retain usable old data and an explicit retry. Do not guess migrations from an already corrupted ID by title. Investigate representative affected series metadata before claiming the reported service case resolved. Empty seasons with no supplied episodes are not fabricated as playable collections.

### Movie seek/resume cause remains unconfirmed

The app accepts VOD seeks only when the player reports a seekable timeline, known positive duration and an available seek command. Resume requires eligible saved progress and revalidates the real timeline when READY. Source review also shows pending resume is consumed on the first READY event; capability timing, saved progress and actual seek failures deserve separate observation. This is a hypothesis, not a diagnosed failure in the reported movie.

Media3's official [troubleshooting guidance](https://developer.android.com/media/media3/exoplayer/troubleshooting#why-are-some-media-files-not-seekable) explains that usable seek metadata or another supported mapping is needed; some files are unseekable. Its [video-seek guidance](https://developer.android.com/media/media3/exoplayer/troubleshooting#why-is-seeking-in-my-video-slow) distinguishes loading the new range from decoder/keyframe work. Server delivery/range behavior, redirects, container/index/timestamps, bitrate/keyframe spacing and player state are investigation candidates. A 4K title label establishes none of them. No universal flag, full-file download, large memory buffer, decoder change or transcoding is proposed.

Proposed VOD-009 is investigation only: compare the privately identified failing movie with one working control, record only sanitized transport/container/timeline/capability/seek/progress outcomes and return the concrete diagnosis and any playback-behavior correction for review. If authorized, use bounded read-only PC provider metadata and stream-header/range samples with strict time/byte limits; do not play or download the whole movie, consume an unbounded response, change provider state or expose authenticated addresses/credentials/title lists. Header claims alone are not proof of successful seeking. Android reproduction, logs or playback require a separate specifically approved Firestick scope; no app start, navigation, installation or setting change is included. If PC evidence is insufficient, identify that limit and request the necessary device check. Preserve working films and current progress/seek guards while the cause is unknown.
